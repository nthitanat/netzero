**Main guideline:** [client-react-architecture.md](client-react-architecture.md) governs the client consistency work. Use the SCSS/theme guides as supporting styling references. `GENERAL_ARCHITECTURE.md` is outside this work’s scope: do not modify it or use it to impose requirements on these fixes.

## Existing shared foundations

The client already has reusable Navbar, Footer, loading, hero/banner, card, tab, and modal components, plus spacing/color tokens and mixins. The findings above identify where their contracts, usage, or documentation are inconsistent; they do not imply that all page-specific markup or fixed layout measurements should become shared components.

## What completing this index would achieve

Fixing and verifying these findings would make the React client substantially more consistent. Completing this list would not, by itself, prove whole-project consistency or production readiness: the audit covers the client, its configuration, and related documentation, not a full backend or deployment review.

| Area | Expected improvement | Examples |
| --- | --- | --- |
| Behavior | Controls accept compatible inputs and display the same underlying state. | Both Follow buttons agree; enrollment and lesson access agree; survey dismissal does not report completion. |
| Navigation | Links resolve to actual records and implemented destinations. | Related courses use `id`; Knowledge Hub and Co-Design links have an intended route or are removed. |
| Appearance and interaction | Shared controls follow consistent styling, theme, language, and keyboard contracts. | Correct icon selectors, reusable action variants, themed catalogs, and accessible gallery triggers. |
| Code organization | Similar responsibilities have predictable owners. | Consistent data loading, obsolete-request handling, and shared catalog components. |
| Documentation and verification | Written conventions match implementation, and meaningful checks detect regressions. | The client architecture guide describes the actual client; build and test checks run successfully. |

Fix shared causes as well as visible symptoms. For INC-01, passing the correct community ID fixes an invalid input, but two Follow buttons can still disagree if each keeps independent state. A complete fix gives follow state one owner and connects both controls to it. Apply the same principle to enrollment and other shared state.

## Recommended fix order

1. **Restore reliable checks (INC-15, INC-16).** Remove build warnings and repair the test setup. Ensure the existing test asserts meaningful current behavior; installing a missing dependency alone is insufficient.
2. **Correct behavior and navigation (INC-01, INC-02, INC-04, INC-09, INC-14, INC-17, INC-18, INC-22).** Resolve follow state/counts, related-course links, obsolete responses, survey outcomes, enrollment, and missing destinations. Coordinate request handling with the data-ownership work in INC-08.
3. **Consolidate shared UI and data patterns (INC-03, INC-05–INC-08, INC-10, INC-11, INC-19–INC-21, INC-23).** Correct icon styling, extract matching catalog/action/header patterns, establish data-loading ownership, align theme usage, and verify localization and keyboard interaction. Preserve intentional page differences.
4. **Finish client documentation alignment and cleanup (INC-12, INC-13).** Remove confirmed unused styles and reconcile client documentation using `client-react-architecture.md` as the main guideline. Update affected guidance during earlier fixes as decisions are made, then review it together at completion.

This is a recommended sequence, not a record of completed implementation. Mark findings **Fixed** only when their verification targets have been met.

## Decisions needed for dependent fixes

- **Following and enrollment:** Define whether these are browser-only prototypes or account-backed features, including persistence after reload, navigation, and a new session. Define the authoritative source for follower counts; omit the count if none exists.
- **Survey completion:** Establish a trusted, verifiable completion signal and distinguish it from dismissal. If the integration cannot verify submission, the UI must not claim verified completion.
- **Missing destinations and contacts:** Decide whether Knowledge Hub and Co-Design belong in the current product. Supply verified contact/social destinations or omit placeholders.
- **Shared conventions:** The updated `client-react-architecture.md` now specifies data-loading ownership, required versus optional files, and permitted shared-component theme usage (INC-13 resolved). Implement those conventions under the relevant source findings and reconcile the supporting SCSS/theme guides under INC-10.

## Completion criteria

- Each resolved finding records the actual change and verification evidence in its final column, including any remaining limitation.
- Affected user flows work end to end, and components that represent the same follow/enrollment state remain synchronized under the chosen persistence contract.
- Navigation reaches intended pages and records; loading, empty, error, and rapid-navigation behavior is verified where affected.
- Shared UI changes are checked at mobile and desktop widths, in Thai and English, and with keyboard interaction where applicable.
- From `glocal-client`, `CI=true npm run build` and `CI=true npm test -- --watch=false --runInBand` pass. Relevant behavioral regressions have meaningful coverage; passing a build alone does not prove functional consistency.
- The client implementation and `client-react-architecture.md` agree on boundaries and required versus optional conventions; supporting SCSS/theme guides align with those decisions. Proposed work is clearly distinguished from current behavior.
- Any claim of broader project consistency is supported by a separate review of the areas outside this index's scope.
